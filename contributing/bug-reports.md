# Bug reports and contributor credit

We distinguish production/usage bugs from audit bugs to recognize the context
contributors add and make useful audits repeatable.

## Production/usage bugs

A production/usage bug is a problem you encountered while using AI SDK to build
or run something. This includes development as well as deployed applications.
Share:

- What you were building and why you used the SDK that way.
- The relevant usage code, SDK and provider versions, and environment.
- What you expected, what happened, and the impact on your application.
- Logs, error messages, and a minimal reproduction or failing test where available.

When a production/usage report leads to a bug fix pull request, we will credit
the issue author with co-authorship. Pull request authors will also be credited
when their work adds valuable input to resolving the report or improves the
quality of its fix.

For example, a report explaining how streaming tool results fail in an
application, why that application streams results, and the observed error adds
usage context that maintainers cannot get by scanning the repository.

## Audit bugs

An audit bug is a finding generated by using agents to scan repository code
without providing additional real usage context beyond what is already in the
repository. We will no longer grant co-authorship for these issues.

For example, asking an agent to inspect streaming code and generate an issue
about a possible failure is an audit contribution, even if the agent also
creates a failing test. A reproduction can confirm a defect, but it does not by
itself establish real usage context.

Instead, please contribute the audit prompts you used through a pull request
to [the audit prompt collection](audit-prompts/README.md). We will accept new
valuable prompts and meaningful improvements to existing prompts, and grant
co-authorship for those prompt contributions. This credit applies to the prompt
contribution; it does not automatically extend to future bug fixes found using
the prompt.

The distinction concerns contributor credit, not whether a defect is valid.
Confirmed audit findings can still identify bugs worth fixing.

## Reporting and triage

1. Search existing issues before opening a report. Add relevant context to an
   existing issue when the problem is already reported.
2. Explain how you discovered the problem. For usage bugs, share your actual
   usage and the reason for it. For audits, identify the prompt you used and
   link its contribution pull request when available.
3. Share observed behavior and supporting evidence. Distinguish a suspected
   problem from a reproduced defect.
4. Link related reproductions, tests, pull requests, and prompt contributions
   so maintainers can trace the relevant work.

Using an agent to investigate or describe a problem you encountered while
using AI SDK does not make it an audit bug. Classify reports using their
discovery and usage context, not their writing style or whether an agent helped.

If the discovery or usage context is unclear, maintainers and triage agents
should request clarification before deciding which credit rule applies. Missing
logs or a reproduction alone do not establish that a report came from an audit.
Evaluate whether the finding is an SDK defect separately from its credit
category. A confirmed audit defect should still be treated as a bug.
